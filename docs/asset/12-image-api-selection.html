文生图 API 选型评估

目标：在剧情对话中「不时插入配图」——不是每轮都出图，而是关键节点（场景转折、新角色登场、重要道具）自动配一张。
评估日期 2026-10-14 · 项目：提线 Marionette · 已核实项目现有图片链路代码
先看结论

项目现有 CloudImageProvider 走的是「兼容 OpenAI 的 /images/generations」协议（adapters/image.py）。这意味着 选平台 = 选一个 base_url + model 字符串，不用改一行代码。

在这个前提下，火山引擎方舟（豆包 Seedream） 是国内场景的最优解：接口路径 /api/v3/images/generations 与现有适配器完全对齐，国内直连、免备案、单张约 ¥0.22–0.30。

一、你的项目有哪些硬约束

选型不能只看模型分数，得先看这个项目的实际情况。我从代码里核实出四条硬约束：

约束代码证据对选型的影响
必须兼容 OpenAI images 协议 adapters/image.py:52-61 组装 {model, prompt, n, size, response_format}，POST 到 {base_url}/images/generations 协议不兼容 = 必须新写一个 Adapter
要能拿 base64（或 URL） image.py:92-97 优先读 b64_json，回退读 url 再下载 两种都支持，兼容性好
服务器在国内、无域名 101.33.117.223，走 HTTP 明文，无 ICP 备案 境外 API（OpenAI / Google）网络不稳 + 合规风险
出图不阻塞对话主流 image_hook.py 注释：「不阻塞对话主流（失败仅置 failed）」 可以接受 10–40 秒出图，异步即可
关键洞察：因为架构是「接口隔离 + 厂商无关」（image_hook.py 顶部明确写「绝不 import 任何厂商 SDK」）， 选型不是不可逆的。换平台 = 改 .env 里的 IMAGE_BASE_URL / IMAGE_MODEL。 所以先选一个能立刻跑的，别为「最优」纠结太久。

四、备选与排除

次选 阿里云百炼（通义万相 / 千问图像）

同样提供 OpenAI 兼容模式（https://dashscope.aliyuncs.com/compatible-mode/v1）， 价格与火山接近。如果你的 DeepSeek key 已经在阿里云体系里，或者想统一账单，这个是很好的选择。 万相和千问的图像能力都在第一梯队。

受限 Google Nano Banana 2

模型本身很强 —— 图内文字渲染、角色一致性（可保持 5 个角色）都是顶级的，价格也便宜。 但两个问题让它不适合当前阶段：

  • 协议不标准 —— 走的是 Gemini 的 generateContent，不是 /images/generations，必须新写一个 Adapter
  • 网络 —— 服务器在国内无域名，直连 Google 不稳，且涉及数据出境合规

建议：等有域名 + HTTPS 之后，再考虑加一个 Gemini Adapter 作为「高质量档」。架构支持多 Provider 切换，值得保留这个可能性。

当前不建议 OpenAI GPT Image 2.5

质量确实第一梯队（榜单第一），但：国内合规风险（境外 API + 无备案域名）、需要代理、 且价格档位极其混乱（同一模型 $0.005 到 $0.211，42 倍差距，容易预算失控）。

不可用 Midjourney

没有公开 API。只有第三方逆向接口，不稳定且违反 ToS。排除。

五、「不时插入图片」的落地建议

重点：不是每轮都出图。每轮出图既贵（一轮 ¥0.22，20 轮 ¥4.4）又打断叙事节奏。建议按「值得画」的时机触发：

触发时机数据来源优先级
节点触发时（node_triggered）导演的 node 事件已有最高
新角色登场cast 变化 / 首个 speaker 变新高
场景切换scene 的 location 变化中
玩家手动点「画一张」前端按钮中
每轮都出—不建议

好在这些数据导演已经在产出了 —— 你上一步做的 S15-1（建议持久化）思路完全一样： 把已经算出来的信号，用来触发一个额外动作。工程量不大。

成本估算：按「每 5 轮配 1 张」的节奏，20 轮的一局 = 4 张 ≈ ¥0.9/局。
对比：目前一局 20 轮的 LLM 成本（导演 1 次 + 各角色 1 次/轮）远高于此。出图不是成本瓶颈。
