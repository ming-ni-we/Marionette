## 项目目录改名尝试与回滚（重要教训）

**经过**：按用户「规划到 WorkBuddy 的一个项目中」的指令，08:51 把会话目录从 `2026-10-09-14-38-58` 搬到新命名的 `C:/Users/user/WorkBuddy/marionette`；08:56 用户要求「恢复到原来的项目名称而不是 workbuddy」，已搬回原路径，`marionette` 空目录删除。

**技术教训（两条，下次别再踩）**：
1. **WorkBuddy 会话目录被客户端进程持有句柄**：`mv` 整个目录报 `Device or resource busy`，只能「建新目录 + 搬内容（`shopt -s dotglob` 才能带上隐藏文件）」；对空目录 `rmdir` 同样可能失败。
2. **客户端把会话工作区绑定在固定路径上**：内容搬走后原路径变空，客户端项目名回退显示为父目录名 `workbuddy` —— 这正是用户看到的「workbuddy」。

**结论**：**不要擅自给会话目录改名**。若真需要正式项目名，应先让用户在客户端侧操作，或改名后立即告知需要重启客户端。项目内涵（「提线」/Marionette）通过 git 仓库名、README、包名前缀 `marionette-`、容器名 `marionette-*` 体现，与目录名解耦。

## 集成测试首次真连 PostgreSQL —— 暴露 4 类缺陷（提交 be693ad）

**背景**：之前集成测试一直 `26 skipped`，从未真跑过。打开 `MARIONETTE_INTEGRATION=1` 后首跑 `83 passed / 9 failed`，全部为真实缺陷。

**缺陷 1（最严重）：集成测试直接读写生产库，造成数据污染**

`conftest.py` 的隔离机制失效。机制链条（探针在容器内确诊）：
- `search_path` = `"mtest_x",public` **确实生效**（打印确认）；
- 但 `relation "mtest_x.cards" does not exist` —— 表没建出来；
- 根因：`Base.metadata.create_all` 默认 `checkfirst=True`，靠 `pg_table_is_visible()` 判存在性。`search_path` 里的 `public` 兜底让 `public.cards` 对本会话"可见" → 误判"表已存在" → **整段 CREATE TABLE 被跳过** → 临时 schema 空无一表 → 查询回落 `public`。
- 修法：`Table.to_metadata(schema=...)` 显式复制全部 `sorted_tables` 到临时 schema 再建；加两道硬守卫（核对 `current_schema()` 与实建表数），失效即 `pytest.exit(returncode=2)`；teardown 加前缀保险。
- **注意**：`search_path` 里的 `public` 不能删 —— `vector`/`pg_trgm` 的类型与操作符装在那里，删了报 `type vector does not exist`。
- 污染后果：生产库被写入 21 张 `栖夜*`、9 张 `倒序*`、3 张 `双标签角色`，世界书由 6 变 9（含我验证时建的 `验证用世界书`）。**待用户确认后清理**。

**缺陷 2：导出/下载遇中文文件名必 500**
`Content-Disposition` 是 HTTP 头，Starlette 对头值做 `encode("latin-1")`，中文抛 `UnicodeEncodeError`（且被通用处理器兜成 500，难定位）。新增 `app/core/text.py::content_disposition()`，按 RFC 6266/5987 输出 `filename="<ascii回退>"; filename*=UTF-8''<percent>`；覆盖 export card/bundle 与 assets content 三处。

**缺陷 3：世界书导入 500 —— 契约与代码漂移**
`wb_import` 返回 `"st_worldbook"`，但 `ImportResult` 的 `Literal` 与 `openapi.yaml` 枚举只有 `st_v1/v2/v3/native`。契约与代码同步补齐。

**缺陷 4：`WorldBookEntry.id` 声明为 UUID 过严**
平台内部（`world_info.py`）本就把 entry id 当不透明字符串，且 ST 用 int id。UUID 化会在创建校验（400）与响应序列化（`ResponseValidationError` → 500）两处同时炸。放宽为 `str`，同步 `schemas.md` §4.2 与 openapi（book 级主键仍 uuid）。

**附带**：`backend/alembic/` 与三方包 `alembic` 同名，ruff 误判一等包 → I001 误报。在 `pyproject.toml` 用 `[tool.ruff.lint.isort] known-third-party = ["alembic"]` 从根上修掉，而非挪导入顺序。

**复验证据（服务器真实 PG）**：集成测试 `106 passed / 0 failed`；跑前跑后 `public` 计数完全一致（`74/8/4/3/0`）→ **零写入**；无 `mtest_`/`probe_` 残留；中文名卡「苏晚晴」导出 json/png/bundle 全 200 且头含 `filename*=UTF-8''%E8%8B%8F...`；世界书导入 201 / `source_format=st_worldbook`；单测 80 passed；ruff 全绿。

**教训（写进 pitfalls.jsonl）**：
1. 用 `search_path` + `create_all` 做测试隔离**不可靠**，必须显式按 schema 建表并加"实建表数 == 元数据表数"的断言。
2. 任何 HTTP 响应头都不允许出现非 ASCII，文件名一律走 RFC 5987 双段式。
3. Pydantic `Literal` 枚举漏值会以 500 而非 400 表现，契约与 `Literal` 必须配单测防漂移。
4. 判断"测试是否真跑过"不能只看 skipped 数 —— 本次 pytest 未装导致集成测试静默没跑，`零写入` 判据一度空过（假 PASS）。**验证前先确认测试真的执行了**。
